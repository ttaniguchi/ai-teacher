go-taskの用途と使い方

作成日: 2026年7月2日

go-taskは、プロジェクトで繰り返すコマンドをTaskfile.ymlに名前付きでまとめるタスクランナーです。開発、テスト、ビルド、コード生成、Docker操作などを「このリポジトリではtask testを打てばよい」という形にそろえられます。

簡潔なQ&A

Q. go-taskは何に使うものですか？
A. よく使う開発コマンドをTaskfile.ymlに定義し、task buildやtask testのように短い名前で実行するための道具です。Makefileの現代版に近く、Linux、macOS、Windowsで同じ手順を共有しやすいのが特徴です。
Q. ライブラリですか、CLIツールですか？
A. 現場では「go-task」と呼ばれがちですが、通常の利用ではGoのライブラリというよりtaskコマンドとして使うCLIツールです。Goで実装されているためこの名前で呼ばれます。
Q. まず何を覚えればよいですか？
A. Taskfile.yml、tasks、cmds、deps、varsの5つを押さえれば、現場の多くのTaskfileを読めます。

用途

go-taskの役割は、プロジェクト固有の作業手順をコマンド化して、チーム全員が同じ入口から実行できるようにすることです。READMEに長い手順を書く代わりに、task setup、task dev、task lint、task testのような形に整理します。

たとえば次のような処理をまとめるのに向いています。

  • ローカル開発環境の起動: docker compose up、APIサーバー起動、フロントエンド起動
  • 品質チェック: formatter、linter、型チェック、テスト
  • ビルドや生成: protobuf、OpenAPI、ORMクライアント、静的ファイル生成
  • CIとローカルの手順統一: CIでもローカルでも同じtask testを呼ぶ

最小の使い方

公式のGetting Startedでは、task --initでTaskfile.ymlを作成し、task タスク名で呼び出す流れが紹介されています。実務では、次のような形をよく見ます。

version: '3'

tasks:
  dev:
    desc: Start local development
    cmds:
      - docker compose up -d
      - pnpm dev

  test:
    desc: Run tests
    cmds:
      - go test ./...

  lint:
    desc: Run linters
    cmds:
      - golangci-lint run

  check:
    desc: Run all checks
    deps:
      - lint
      - test

この例では、task devで開発環境を起動し、task testでテストを実行します。task checkはlintとtestに依存しており、まとめて検証したいときの入口になります。

現場で読むポイント

項目 意味 見るポイント
tasks 実行できるタスクの一覧 どの作業が標準化されているかを見る
cmds タスク内で実行するコマンド 実際に何が動くか、危険な操作がないかを見る
deps 先に実行する依存タスク 検証やビルドの前提処理を把握する
vars Taskfile内で使う変数 環境名、出力先、イメージ名などの差し替え箇所を見る
env タスク実行時の環境変数 公開してよい値だけが書かれているか確認する
includes 別のTaskfileの読み込み モノレポや役割別タスクの分割を追う

Makefileとの違い

Makefileも同じようにコマンドをまとめられますが、もともとはビルド対象ファイルの依存関係を扱う道具です。go-taskはYAMLでタスクを定義し、説明文、変数、環境変数、Taskfileの分割、ファイル変更に基づくスキップなど、日常の開発タスクを整理しやすい形になっています。

特にWindowsを含むチームや、Docker、Node.js、Go、Terraformなど複数ツールをまたぐ現場では、シェルスクリプトやMakefileの癖を減らし、入口をtaskに寄せられる点が便利です。

導入の流れ

  1. 公式手順に沿ってtaskコマンドをインストールする。macOSならHomebrew、Goプロジェクトならgo tool経由も選択肢になります。
  2. リポジトリ直下にTaskfile.ymlを置く。
  3. READMEや口頭で共有していた手順を、setup、dev、test、lint、buildなどの名前にする。
  4. CIでは複雑なコマンド列を直接書く代わりに、可能ならtask checkのような共通入口を呼ぶ。

注意点

Taskfile.ymlは便利ですが、何でも詰め込むと「中身を見ないと怖いコマンド」になります。削除、デプロイ、DB変更のような影響の大きいタスクには、名前、説明、実行条件を明確にしておくのが安全です。

また、envやdotenvを使う場合でも、APIキーやパスワードをTaskfileに直接書かないでください。Taskfileはリポジトリに残る共有設定なので、公開されても問題ない値だけを置くのが基本です。

要点

go-taskは、開発作業の「標準入口」を作るためのタスクランナーです。現場で見かけたら、まずTaskfile.ymlを開き、tasksの一覧、各タスクのcmds、依存関係のdepsを読むと全体像をつかめます。使う側としては、task --listで実行可能なタスクを確認し、task testやtask devのように呼び出すところから始めれば十分です。
