Go / バックエンドAPI

GoでWeb APIバックエンドを構築する方法

作成日: 2026年6月4日

GoでAPI群を作る場合、巨大なフレームワークに最初から寄せるより、標準ライブラリのnet/httpを土台にし、必要な範囲でルーター、ミドルウェア、OpenAPI、DBアクセス、テストを組み合わせる実装がよく使われます。

簡潔なQ&A

Q. GoでWeb APIを作るとき、定番の実装方法はありますか？
A. あります。小さめなら標準のnet/http、少し大きくなるならchi、素早いREST APIならGinやEcho、Express風の書き味や高性能を重視するならFiber、OpenAPIを強く管理したいならHumaやOpenAPIコード生成を使う構成が候補になります。
Q. まず何を選ぶのが無難ですか？
A. 新規の業務APIなら、まずnet/httpまたはchiを基準に考えるのが堅実です。標準のhttp.Handler互換に寄せると、ミドルウェア、テスト、移行の自由度を残しやすいからです。
Q. フレームワーク選び以外で大事な実装プラクティスは？
A. ハンドラーを薄くする、サービス層とDB層を分ける、context.Contextを伝播する、JSONエラー形式を統一する、httptestでHTTP境界をテストする、OpenAPIやスキーマを早めに整える、といった点が重要です。

GoのWeb API開発の考え方

Goのバックエンド開発では、Ruby on RailsやNestJSのような大きなフレームワークを中心に据えるより、標準ライブラリと小さな部品を組み合わせる設計がよく採られます。HTTPサーバー、ハンドラー、コンテキスト、テスト、SQL接続など、基礎になる部品が標準ライブラリに揃っているためです。

特にGo 1.22以降は、標準のnet/http.ServeMuxがHTTPメソッド指定やパスワイルドカードに対応し、単純なREST APIであればサードパーティのルーターなしでも読みやすく書けます。まず標準機能で足りるかを見て、ルートグループ、ミドルウェア管理、バリデーション、OpenAPI生成などが必要になったら追加のライブラリを検討するとよいです。

よく使われる選択肢

選択肢 向いている場面 見方
net/http 小規模API、社内API、依存を少なくしたいサービス 標準ライブラリだけで完結しやすい。Go 1.22以降はGET /users/{id}のようなルーティングも扱いやすい。
chi 中規模以上のREST API、標準http.Handler互換を保ちたいAPI 軽量なルーター。ルートグループ、サブルーター、ミドルウェア構成を整理しやすく、標準ライブラリとの相性がよい。
Gin 素早くREST APIを作りたい、情報量や利用例の多さを重視したい ルーティング、JSONレスポンス、バインディング、ミドルウェアがまとまっている。独自Contextに寄るため、標準http.Handler互換だけで設計したい場合は確認が必要。
Echo 軽量さと機能のバランスが欲しいWeb API ルーティング、ミドルウェア、バインディング、バリデーションなどをまとめて扱える。Ginと同じく、フレームワークのContextを前提にした書き方になる。
Fiber Express風のAPI、パフォーマンス志向、Node.js経験者が多いチーム fasthttp上に作られており高速志向。標準net/httpとは土台が異なるため、互換性やContext値の扱いを理解して使う。
Huma OpenAPI、型付き入出力、ドキュメント生成を重視するAPI API実装からOpenAPI 3.1などの仕様書を生成しやすい。クライアント生成や契約管理を重視するチームに向く。

実装パターン1: 標準ライブラリ中心

最小構成では、http.NewServeMux()にルートを登録し、各ハンドラーでJSONを返します。Go 1.22以降なら、メソッドとパスパラメータをルートパターンに含められます。

mux := http.NewServeMux()

mux.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")

    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(map[string]string{
        "id": id,
    })
})

server := &http.Server{
    Addr:    ":8080",
    Handler: mux,
}

log.Fatal(server.ListenAndServe())

この形は依存が少なく、http.Handler互換のミドルウェアやhttptestによるテストと合わせやすいのが利点です。ルート数が増えてグループ化や共通ミドルウェアの見通しが悪くなったら、chiなどを検討します。

実装パターン2: chiで薄く構成する

chiは標準net/httpに近い感覚を保ちながら、ルートグループやミドルウェアを整理できます。大きめのREST APIでも、ハンドラーをhttp.HandlerFuncとして保ちやすいのが強みです。

r := chi.NewRouter()
r.Use(middleware.RequestID)
r.Use(middleware.Logger)
r.Use(middleware.Recoverer)

r.Route("/users", func(r chi.Router) {
    r.Get("/{id}", getUser)
    r.Post("/", createUser)
})

http.ListenAndServe(":8080", r)

実装パターン3: GinやEchoで素早く作る

GinやEchoは、ルーティング、JSONレスポンス、バインディング、ミドルウェアなどをフレームワーク側でまとめて提供します。チュートリアルやサンプルが多く、APIを素早く立ち上げたい場合に選ばれやすいです。

r := gin.Default()

r.GET("/ping", func(c *gin.Context) {
    c.JSON(http.StatusOK, gin.H{"message": "pong"})
})

r.Run(":8080")

一方で、ハンドラーがフレームワーク独自のContextに結びつきやすいため、将来別のルーターへ移したい場合や、標準http.Handlerで統一したい場合は、アプリケーションロジックをハンドラーの外に逃がしておくと扱いやすくなります。

実装パターン4: OpenAPI起点またはOpenAPI生成

外部公開API、複数クライアントが使うAPI、フロントエンドと並行開発するAPIでは、OpenAPIを早めに整える価値が高くなります。Humaのように実装から仕様書を生成する方法、OpenAPI定義からサーバーやクライアントを生成する方法、コメントやアノテーションから生成する方法があります。

どの方式でも、リクエスト/レスポンスのスキーマ、エラー形式、認証方式、ページネーション、バージョニングをAPI契約として明示することが重要です。

実務でのプラクティス

ハンドラーを薄くする

HTTPハンドラーには、入力の取り出し、認証済みユーザー情報の確認、サービス呼び出し、レスポンス変換だけを置きます。DBアクセスや複雑な業務処理はサービス層やリポジトリ層へ分けると、テストしやすくなります。

Contextを必ず伝播する

DBクエリ、外部API呼び出し、キュー処理などにはr.Context()を渡します。クライアント切断、タイムアウト、キャンセルを下位処理へ伝えられるため、APIサーバーのリソースを無駄に保持しにくくなります。

エラー形式を統一する

APIごとにエラーJSONの形がばらつくと、クライアント実装と監視がつらくなります。たとえばcode、message、details、request_idのような共通形式を用意し、バリデーションエラー、認証エラー、業務エラー、内部エラーをHTTPステータスと対応づけます。

ミドルウェアを入口に集約する

リクエストID、構造化ログ、panic recovery、CORS、認証、レート制限、メトリクス、トレースはミドルウェアとして入口に集約します。ただし、ビジネスルールまでミドルウェアへ入れると追いにくくなるため、横断的な関心事に絞るのが無難です。

HTTP境界のテストを書く

net/http/httptestを使うと、実際のHTTPサーバーに近い形でハンドラーをテストできます。単体テストではサービス層を直接テストし、結合テストではルーター全体にリクエストを流す、という分け方が扱いやすいです。

選び方の目安

状況 候補 理由
依存を少なく、長く保守したい net/http / chi 標準APIとの距離が近く、移行やテストの自由度を残しやすい。
REST APIを短期間で立ち上げたい Gin / Echo JSON、バインディング、ミドルウェアなどの開発体験がまとまっている。
Express経験者が多い、速度を強く意識する Fiber Express風の書き味で、高性能志向の設計。ただしnet/http互換性は事前確認が必要。
API契約やクライアント生成が重要 Huma / OpenAPIコード生成 仕様書、型、ドキュメント、クライアント生成を開発フローに入れやすい。

要点

GoのAPI開発では、まずnet/http互換を中心に考えると設計の自由度を残しやすくなります。小さなAPIは標準ライブラリで十分なことが多く、ルートやミドルウェアが増えたらchi、開発速度を重視するならGinやEcho、OpenAPI契約を重視するならHumaやコード生成を選ぶ、という整理が実務的です。
