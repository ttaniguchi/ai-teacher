JavaScript / Webフレームワーク

Honoの概要と使い方

Honoは、Web標準のRequest/Responseを軸にした軽量なTypeScript向けWebフレームワークです。Cloudflare Workers、Deno、Bun、Node.js、各種サーバーレス環境など複数の実行環境で、ほぼ同じアプリケーションコードを動かせる点が大きな特徴です。

簡潔なQ&A

Q. Honoってどんなフレームワークですか？
A. Expressに近い書き味でAPIや小さなWebアプリを作れる、軽量・高速・TypeScript中心のWebフレームワークです。Web標準APIを使うため、Node.js専用ではなくEdgeやサーバーレスにも載せやすい設計です。
Q. 何が得意ですか？
A. 小さなAPI、BFF、Webhook、プロキシ、Edgeアプリ、モノレポ内の軽量バックエンドに向いています。ルーティング、ミドルウェア、バリデーション、RPC的な型共有を少ないコードで始められます。
Q. NestJSやExpressと比べると？
A. NestJSほど大きな設計の型はありませんが、そのぶん軽く始められます。Expressより現代的なTypeScript体験とマルチランタイム対応を意識しており、FastifyよりWeb標準とEdge適性に寄せた選択肢です。

Honoの位置づけ

Honoは、HTTPリクエストを受けてレスポンスを返すためのWebアプリケーションフレームワークです。画面全体を構築するメタフレームワークではなく、基本的にはAPIサーバー、BFF、Webhook受信、プロキシ、Edge上の小さな処理を書くための道具と考えると理解しやすいです。

特徴的なのは、Web標準のRequest、Response、fetchに寄せていることです。Node.jsのreq/resに強く依存しないため、Cloudflare Workers、Deno、Bun、Vercel、Netlify、AWS Lambda、Node.jsなど、複数の環境へ展開しやすくなっています。

主な特徴

軽量で始めやすい

Honoの基本形は、new Hono()でアプリを作り、app.get()やapp.post()でルートを登録するだけです。Expressに近い感覚で読めるため、Node.jsのAPI開発に慣れている人なら導入の心理的負担は小さめです。

Web標準ベースでマルチランタイム

同じルーティングやミドルウェアのコードを、実行環境ごとのエントリーポイントに載せ替えやすいのがHonoの強みです。特にEdge Runtimeやサーバーレスでは、依存が小さく起動が軽いこと、Web標準APIに沿っていることが効きます。

TypeScriptとの相性がよい

ルートパラメータ、Context、バリデーション、Hono Clientを使ったRPC風の型共有など、TypeScriptでAPI境界を扱いやすくする仕組みがあります。Zodなどのバリデーションライブラリと組み合わせる構成もよく使われます。

ミドルウェアとヘルパーが揃っている

CORS、JWT、Basic/Bearer認証、ログ、ETag、セキュリティヘッダー、Cookie、Streamingなどのミドルウェアやヘルパーが用意されています。必要なものを足していく、小さく組み立てるタイプのフレームワークです。

基本的な使い方

新規プロジェクトは、公式のcreate-honoで作成できます。テンプレート選択でNode.js、Cloudflare Workers、Bun、Denoなどの実行環境を選びます。

npm create hono@latest my-app
cd my-app
npm install
npm run dev

最小のAPIは次のように書けます。

import { Hono } from 'hono'

const app = new Hono()

app.get('/', (c) => {
  return c.text('Hello Hono')
})

app.get('/users/:id', (c) => {
  const id = c.req.param('id')
  return c.json({ id })
})

export default app

ミドルウェアはapp.use()で追加します。たとえばログとCORSを入れる場合は次のようになります。

import { Hono } from 'hono'
import { cors } from 'hono/cors'
import { logger } from 'hono/logger'

const app = new Hono()

app.use(logger())
app.use('/api/*', cors())

app.get('/api/health', (c) => c.json({ ok: true }))

export default app

他のフレームワークとの比較

フレームワーク 得意なこと Honoと比べた見方
Express Node.jsの定番APIサーバー。情報量、既存ミドルウェア、採用実績が非常に多い。 HonoはExpressに近い書き味を保ちつつ、TypeScript体験、軽さ、Edge/サーバーレス適性を現代寄りにした選択肢。
Fastify Node.jsで高性能なAPIサーバーを作る。スキーマ、プラグイン、バリデーションの仕組みが強い。 Node.js中心で堅く作るならFastify、Web標準と複数ランタイムを重視するならHonoが合いやすい。
NestJS DI、Module、Controller、Serviceなどを備えた構造化バックエンド。中規模以上のチーム開発に向く。 Honoは設計の自由度が高く軽い。NestJSは初期学習コストが高い代わりに、大規模化したときの型を先に用意してくれる。
Next.js Route Handlers Reactアプリと同じプロジェクト内でAPIを持つ。画面、認証、サーバー処理を一体で扱いやすい。 画面中心ならNext.js、API単体や複数ランタイム展開を切り出したいならHonoが扱いやすい。
Elysia Bunを中心に高速なAPIを作る。型推論とスキーマ統合の開発体験が強い。 Bun前提で攻めるならElysia、ランタイムを固定しすぎずWeb標準ベースで広く動かすならHonoが選びやすい。

メリット

  • コード量が少なく、APIやWebhookをすぐに書き始められる。
  • Web標準APIを軸にしているため、Edge、サーバーレス、Node.jsなどに展開しやすい。
  • TypeScriptの型補完が効きやすく、ルートやContextの見通しがよい。
  • ミドルウェアとヘルパーが公式に揃っており、小さな構成から段階的に拡張できる。
  • モノレポ内で、フロントエンドとは独立した軽量API層を作りやすい。

デメリットと注意点

  • NestJSのようなModule、DI、アーキテクチャ規約は標準では強くないため、大規模化すると設計ルールを自分たちで決める必要がある。
  • Expressほど歴史が長いわけではないため、特定ミドルウェアや社内ノウハウがExpress前提の場合は移行コストが出る。
  • Node.js専用ライブラリを多用すると、せっかくのマルチランタイム性が弱くなる。
  • Edge環境ではファイルシステム、長時間接続、TCP接続、ネイティブ依存などに制約があるため、Honoを使えば何でも同じように動くわけではない。
  • 自由度が高いぶん、認証、エラー形式、ディレクトリ構成、テスト方針を早めに揃えないとプロジェクトごとの差が出やすい。

選び方の目安

状況 選びやすい候補 理由
Cloudflare WorkersなどEdgeでAPIを作りたい Hono Web標準ベースで、軽量なルーティングとミドルウェアを載せやすい。
小さなBFFやWebhookを素早く作りたい Hono / Express どちらも書き始めが軽い。新規でTypeScript中心ならHonoが気持ちよく使いやすい。
Node.jsで高性能・堅牢なAPIを作り込みたい Fastify Node.js中心のプラグイン、スキーマ、バリデーション設計が強い。
大きな業務APIをチームで長期運用したい NestJS Module、DI、Controller、Serviceなど、設計の型をチームで共有しやすい。
Reactアプリの中にAPIを同居させたい Next.js Route Handlers 画面、サーバー処理、認証、デプロイ単位をまとめやすい。

要点

Honoは「軽く書けるExpress風のAPIフレームワーク」を、TypeScript、Web標準、Edge/サーバーレス時代に合わせて作り直したような存在です。小さく始めて複数ランタイムへ展開したい場合に強く、逆に大規模な業務アプリの設計規約までフレームワークに任せたい場合はNestJSやFastifyのほうが合うことがあります。
