TypeScript / コーディング基盤

TypeScriptの静的解析と自動整形ツールの現在地

TypeScript / JavaScript の規約基盤は、今も「ESLint + typescript-eslint + Prettier」が最も広い互換性を持つ標準解です。一方で、後継候補は Rust や Go 系の高速実装へ進み、Biome と Oxlint が「速く、少ない設定で、CI とエディタを統一する」方向へ進化しています。

簡潔なQ&A

Q. 現在もっとも支持されている基盤は何ですか？
A. 互換性・プラグイン・採用実績まで含めると、まだ ESLint + typescript-eslint + Prettier が最も堅い標準です。React、Next.js、Node.js、テスト、アクセシビリティ、import ルールなど周辺エコシステムが強いからです。
Q. Prettier や Biome の後継はどう進化していますか？
A. Prettier は「整形専用」の安定ツールとして残り、Biome は Rome の公式フォークとして「formatter + linter + import 整理」をまとめる方向に進化しました。Oxlint は Oxc コンパイラ基盤の高速 linter として、ESLint 互換ルールや type-aware linting を広げています。
Q. 新規プロジェクトでは何を選ぶべきですか？
A. 迷うなら ESLint + typescript-eslint + Prettier。速度と設定の少なさを優先する小〜中規模プロジェクトなら Biome。大規模 monorepo や CI 高速化では Oxlint + 必要部分だけ ESLint の段階移行が現実的です。

結論：標準はまだ ESLint 系、進化の中心は高速統合ツール

「最も支持されている」を、npm ダウンロード数だけではなく、フレームワーク統合、プラグイン資産、既存プロジェクトの採用、移行リスクの低さとして見るなら、2026年5月時点の標準解はまだ ESLint 系です。TypeScript では typescript-eslint が ESLint の flat config 前提で推奨設定を提供し、型情報を使う lint の入口にもなっています。

ただし、開発体験の流れは明確に変わっています。昔は「TypeScript は tsc、lint は ESLint、format は Prettier、import 整理は別プラグイン」のように役割分担していました。現在は Biome や Oxlint のように、パーサ・解析・診断・自動修正を単一の高速基盤に寄せる方向が強くなっています。

主要ツールの役割

ツール 主な役割 強み 注意点
ESLint JavaScript / TypeScript の lint 基盤 プラグイン資産が圧倒的。React、アクセシビリティ、import、テストなどのルールを組み合わせやすい。 設定が複雑になりやすい。大規模 CI では速度が課題になりやすい。
typescript-eslint ESLint で TypeScript を理解するための parser / plugin / config 型情報を使うルールを扱える。ESLint flat config の公式的な導線がある。 型情報を使う lint は便利だが遅くなりやすい。tsconfig 設計の影響を受ける。
Prettier 自動整形専用 意見の強い formatter として安定。多言語・エディタ統合が強い。 lint ではない。コード品質やバグ検出は ESLint 等に任せる。
Biome formatter + linter + import 整理 速い。設定が少ない。Prettier / ESLint の一部用途を1つにまとめられる。 ESLint の全プラグインを置き換えるものではない。フレームワーク固有ルールが必要なら併用判断が必要。
Oxlint Oxc 基盤の高速 linter ESLint 互換ルールを広く取り込み、大規模 CI の高速化に向く。type-aware linting と複数ファイル解析も進む。 既存 ESLint プラグインの特殊挙動に依存する場合は段階移行が現実的。

後継ツールは何を置き換えようとしているのか

Prettier は「なくなる」より「専用ツールとして残る」

Prettier は今も「opinionated code formatter」として、多くの言語とエディタに対応する整形専用ツールです。強みは、整形の議論を減らすことに徹している点です。後継ツールが登場しても、既存プロジェクトでは Prettier を維持する価値は高いままです。

Biome は Rome の思想を現実的に引き継いだ統合ツール

Biome は Rome の公式フォークで、Rome の「Web toolchain を1つにまとめる」思想を引き継いでいます。現在の実用上の中心は formatter、linter、import 整理です。Biome の linter は推奨ルールを備え、整形に関する指摘は linter ではなく formatter に分離する設計です。これにより、規約の責務が分かりやすくなります。

Oxlint は「ESLint の高速互換レイヤー」に近づいている

Oxlint は Oxc コンパイラスタック上の JavaScript / TypeScript linter です。目標は単なる軽量 linter ではなく、ESLint core ルール、TypeScript ルール、React や Jest などの主要プラグイン領域を広くカバーし、大規模リポジトリでも高速に動かすことです。特に CI 時間が問題になっている組織では、ESLint を全面置換する前に、Oxlint を先に走らせ、重複ルールを ESLint 側で無効化する段階移行が取りやすいです。

選定の実務目安

状況 推奨構成 理由
一般的な React / Next.js / Node.js プロジェクト ESLint + typescript-eslint + Prettier 互換性が最も高く、既存のフレームワーク設定やプラグイン資産を使いやすい。
新規の小〜中規模 TypeScript プロジェクト Biome から開始 整形と基本 lint を少ない設定で始められる。必要になったら ESLint を追加できる。
大規模 monorepo / CI が遅い Oxlint + ESLint の段階移行 高速なルールを Oxlint に寄せ、ESLint は未対応または特殊なルールだけ残せる。
チームで規約議論を減らしたい Prettier または Biome formatter 整形は formatter に任せ、レビューでは設計・仕様・安全性を見るほうが効率的。
型に基づくバグ検出を重視 tsc --noEmit + typed lint formatter や構文 lint では検出できない Promise、nullable、型境界の問題を拾える。

導入時の考え方

重要なのは「全部入りの流行ツールを入れる」ことではなく、規約の責務を分けることです。

  • 型チェック：tsc --noEmit。型の正しさは TypeScript 本体に任せる。
  • 静的解析：ESLint / typescript-eslint / Oxlint / Biome linter。バグ、危険な書き方、チーム規約を扱う。
  • 自動整形：Prettier / Biome formatter / Oxfmt。スタイル議論を機械に寄せる。
  • CI：まず高速なチェックを先に走らせ、重い type-aware lint は必要範囲に絞る。

この分離を守ると、将来 ESLint から Oxlint へ移す、Prettier から Biome formatter へ移す、といった変更も小さくできます。

よくある誤解

  • 「Biome を入れれば ESLint は不要」とは限りません。基本的な lint と整形は置き換えやすいですが、フレームワーク固有ルールや社内ルール、特殊な ESLint plugin に依存している場合は併用が現実的です。
  • 「Prettier と ESLint は競合する」というより、役割が違います。Prettier は整形、ESLint は静的解析です。整形ルールを ESLint に持たせすぎないほうが保守しやすいです。
  • 「速い linter は浅い」とは限りません。Oxlint は type-aware linting や multi-file analysis を進めています。ただし、すべての ESLint plugin 挙動が完全互換という前提ではなく、移行時にはルール差分を確認します。

要点

2026年5月時点では、もっとも安全な標準解は ESLint + typescript-eslint + Prettier です。後継の本命は用途で分かれ、Biome は「少ない設定で formatter と基本 lint を統合する」方向、Oxlint は「ESLint 資産を高速なコンパイラ基盤へ移す」方向に進化しています。新規は Biome から始めてもよいですが、既存・大規模・フレームワーク依存が強い場合は ESLint 系を残しながら段階移行するのが堅実です。
